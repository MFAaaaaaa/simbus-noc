# 逐指令时序与共享总线（2026-11-03）

本轮在原有 NoC 模型之外增加真正的单共享介质与请求仲裁。旧版 `run.ini` 默认仍使用 RingNoC 和类别周期，旧实验数值不能混入新的时序/总线配置。新实验使用 `run-bus.ini`。

## 1. 外置逐指令周期表

`--timing-table isa-timing.ini` 支持 `addi = 1` 和 `vadd.vv = { base=2, lanes=8 }`。优先查询具体指令名，未配置项回退到原有类别周期。`vle8/16/32/64.v` 与 `vse8/16/32/64.v` 分别可配置。`vector.default` 给未逐项覆盖的向量 ALU 设置 `base + ceil(vl/lanes)`，无该设置时保留旧 `lat-valu`。不支持的语义仍由核心白名单拒绝，周期表不会扩展 ISA 功能。

新示例表的 vadd 在 vl=8 时占位3周期，在 vl=256 时占位34周期。实际合法VL受VLEN=256、SEW、LMUL限制，不能假定任何配置都能设置VL=256。0/负周期、0 lanes、重复项、未知指令、溢出等报错。

汇报口径：核心单发射、顺序且计算指令无发射重叠，因此这里用一个执行占位周期参数建模，不单独建模流水线吞吐。它不等于真实芯片指令 latency，也不是完整指令 CPI。取指译码、访存注入、网络和内存响应等待另外计入；异步 MMIO 可以与本地计算重叠。示例周期与lane数是待标定模型参数，不是硬件实测值。

## 2. IBus 双实现

`IBus` 继承现有 `BusInterfaceV2`，保持 can_send/send/can_recv/recv/apply_next_tick 调用约定。

- `RingNoC` 包装原双环网络，不修改 NoC 库。
- `SharedBus` 所有请求、响应共用一条非抢占介质，服务周期为地址拍与数据拍之和，与消息字节数无关，适用于固定大小事务的首版模型。
- 每次只授权一个发送者。一个事务完成后才能授权下一个，不会流水重叠。
- 响应通道优先，以免请求流饿死响应并造成协议级停顿。请求端支持 `rr` 和按端口号递增的 `fixed`。响应不重置请求RR指针。
- 每源有限发送队列；可选目的端消息额度，在send成功时预留、recv后释放。`can_send` 不检查具体目的端，因此仍必须检查send返回值。
- 每master记录请求/授权数、队列请求·周期、每消息授权等待均值/p99、最长等待和长等待阈值事件。阈值事件每消息只计一次，包含仍未授权的消息，不表示已证明永久饥饿。未丢弃请求，无自动超时取消。
- busy/idle按每个模拟tick互斥计数，utilization=busy/(busy+idle)。NoC原有packet统计与SharedBus完整消息统计不可直接对比。

## 3. 持续总线压力与三张图

```bash
./build/bus_saturation build/results/new-bus-saturation.csv
python3 scripts/plot_bus_saturation.py build/results/new-bus-saturation.csv
```

生成吞吐、延迟和仲裁公平性图（PNG、SVG），CSV存在时拒绝覆盖。实验使用4个开放式源、固定随机种子20261103，绕开Atomic单未完成事务对offered load的限制。共享总线每消息4周期，每个内存请求产生一条请求、一条响应，理论容量1/8=0.125请求/周期。真实MemoryController服务1周期、队列64，必须同时验证内存利用率和队列满计数，不能只凭调低内存延迟宣称总线瓶颈。

预热2000周期，观测20000周期。offered load是外生到达率，含未接纳与丢弃的到达，不是总线接受率。源端有有限积压上限，报告drops与censored。过载时积压增长，完成请求延迟包含软件源端排队，且存在未完成样本，所以不能宣称测到了稳态平均延迟。授权等待直方图与阈值事件覆盖预热和观测全程。

均衡场景用于吞吐/延迟扫描。热点场景中master0产生80%的到达，在聚合0.4请求/周期下比较轮询和固定优先级。RR衡量持续有请求的master获得服务的机会，不保证不同提供负载的master完成量相等。固定优先级低优先级完成量为0是有限窗口内饥饿证据。

发布数据：`docs/results/2026-11-03/bus-saturation-verified.csv`。首次试验发现响应重置RR指针，修复并加入测试后重新扫描，初稿不作为结论数据。

## 4. CSR 与并发 MMIO

CSR直接映射同一个适配器，MMIO与CSR可以操作同一组状态，没有另造一条绕开总线的捷径。

| CSR | 含义 | MMIO偏移 |
|---|---|---|
| 0x7c0 | BUS_ADDR | 0x00 |
| 0x7c1 | BUS_CMD，1读2写 | 0x18 |
| 0x7c2 | BUS_WDATA | 0x08 |
| 0x7c3 | BUS_RDATA，只读 | 0x28 |
| 0x7c4 | BUS_STATUS | 0x20 |
| 0x7c5 | BUS_SIZE | 0x10 |
| 0x7c6 | 完成队首事务ID，只读 | 0x40 |
| 0x7c7 | 写1弹出完成队首 | 0x48 |

`--mmio-depth 1`保留旧忙时拒绝语义。大于1时可在忙时更新配置寄存器并持续提交命令。容量限制未完成事务加未取走结果的总数，满时拒绝新命令并置ERROR，原请求不丢失。每条命令快照地址/数据/宽度，事务ID使用高半区，与普通访存分离。适配器可每tick尝试发送一条未发送请求并接收一条响应，多个目标事务可以同时在总线上。完成结果按响应到达顺序入FIFO，用结果ID识别对应命令。

新增MMIO偏移0x30读取深度、0x38读取未完成数、0x40读取结果ID、0x48弹出结果、0x50读取队首结果DONE/ERROR状态。读RDATA不会弹出，软件必须显式POP释放容量。全局ERROR为粘滞位，忙时可用STATUS清除。目标响应错误也在结果状态中报告。

`csr_bus_smoke.S`连续发4笔CSR写，不逐笔轮询，经Fence排空后核对数据和弹出结果，最后用CSR读回验证。在RingNoC/SharedBus上均有4Hart集成测试。MMIO多Outstanding由C++接口测试覆盖。

## 5. Fence 与统计口径

Fence先等待本Hart所有已发数据事务与适配器请求排空，再执行固定Fence周期。核心顺序执行，普通/向量子事务本来就在下一条指令取指前完成。Fence不等待软件弹出完成FIFO，不清理其他Hart请求，也不提供未建模的Cache维护。核心正常停止后调度器继续排空适配器。

CSV schema升级为3，拒绝向旧schema追加。新增普通访存每请求往返均值/p99、每请求注入等待、MMIO每请求均值/p99、Hart响应等待占比及总线利用率、仲裁参数与实际逐指令时序快照。

普通访存延迟从首次实际注入尝试到匹配响应消费，包含注入重试，按子事务计数，不包含此前执行准备和等待MMIO端口；MMIO延迟从命令入队到响应消费。p99采用精确直方图nearest-rank，无样本返回0。直方图不保存每个样本，但长时间运行的不同延迟桶仍可能增长。超时运行的均值/p99只涵盖完成请求，不能忽略未完成事务。

Hart等待占比=各Hart响应等待周期之和/各Hart活跃周期之和，范围0～1，不再除以全局tick。普通请求平均注入等待=注入失败累计周期/完成子事务数，只在请求全完成时作为完整均值。MMIO等待与核心可能重叠，不能叠加为全局占比。run.py的配置快照额外保存时序文件全文和SHA256。
